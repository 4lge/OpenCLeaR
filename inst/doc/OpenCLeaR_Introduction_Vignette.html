Introduction to OpenCLeaR

This document serves as a comprehensive guide and architectural reference for the OpenCLeaR framework. We step sequentially through three stages of workload density – from simple element-wise operations to single-step back-propagation gradients, and finally to a completely enclosed multi-epoch neural network training loop. This structure highlights how data persistence and JIT-caching eliminate bus bottlenecks and maximize the parallel performance of OpenCL devices, in this case a mobile Nvidia RTX 4080.

Part 1: The ‘Hello World’ Example of Parallel Computing (Sigmoid Vector Addition)

We begin with an element-wise addition of two vectors \(a\) and \(b\) into a target vector \(c\), followed by a logistic sigmoid transformation. This minimal functional setup demonstrates how OpenCLeaR links external mathematical dependencies (math_lib) and interfaces vectors.

Section 1.1: Generating Shared Mathematical Helpers

The math helper library acts as a static compile-time baseline. It provides inline functions for the forward logistic sigmoid transformation and its corresponding analytical first-order derivative used during the gradient backpropagation phase.

libkernel_src <- '
static inline real compute_sigmoid(real x) {
    return (real)1.0f / ((real)1.0f + exp(-x));
}
'
writeLines(libkernel_src, "./libkernel.cl")

Note that we use an abstract ‘real’ type instead of ‘float’ or ‘double’ it will be replaced with the appropriate floating point type depending on the capability of your OpenCL device later on the fly. Also note that we write floating point constants as ‘(real)1.0f’ forcing them into the right format avoiding compiler warnings about ‘double’ constants appearing in a ‘float’ only environment.

Furthermore the function is defined as ‘static inline’ which instructs the OpenCL compiler built into your OpenCL driver to only include this function if it is actually call by one of your kernels. This is important because OpenCL binaries are not dynamically linked as you may be accustomed to by your C/C++ experience otherwise.

In this case we save the helper library in the actual working directory and are also referencing it this way ‘./libkernel.cl’. If we reference it as ‘libkernel.cl’ it will be searched under the ‘kernel’ sub directory of the installed library (which is ‘system.file(“kernel”, package = “OpenCLeaR”)’). The helper library located there under this name contains a collection of ‘[dpqr]’ functions like ‘runif’ which can be used in your OpenCL code with similar but not completely equal call signatures as in R itself. We will use them in a later example.

Section 1.2: Generating the Element-Wise OpenCL Kernel

The kernel distributes the element-wise addition with application of the sigmoid function across uniform global 1D execution pipelines. Each execution thread resolves its matching array coordinates using its unique worker index, accumulates the vector points, and saves the output directly into the global result vector.

vector_kernel_src <- '
__kernel void sigmoid_add_kernel(__global const real* a,
                                 __global const real* b,
                                 __global real* c,
                                 const int n) {
    int id = get_global_id(0);
    if (id < n) {
        real sum = a[id] + b[id];
        c[id] = compute_sigmoid(sum);
    }
}
'
writeLines(vector_kernel_src, "./sigmoid_add_kernel.cl")

This kernel is again written to the working directory and referenced later as ‘./sigmoid_add_kernel.cl’. If we reference it as ‘sigmoid_add_kernel.cl’ without leading ‘./’ it will be read by ‘oclFunction’ from ‘system.file(“kernel”, package = “OpenCLeaR”)’ in the same way as the helper library.

Note here that OpenCL C does imply some additional restrictions on the scope of variables:

  • A variable defined without any prefix is ’__local’,
  • a variable defined with the prefix ’__global’ is shared with other threads and write access to indices other than ‘get_global_id(0)’ may cause trouble,depending on your algorithm layout.
  • A variable with prefix ’__constant’ is local and immutable. Such declarations have to appear at the very beginning of the kernel.
  • There is no ‘malloc()’, array pointers enter the kernel as ’__global’ arguments.

Section 1.3: Creating the Host-Device Rcpp Vector Interface

The host interface configures the memory transactions for the argument vectors passed from R. It marshals host-allocated memory streams into low-level OpenCL memory nodes, commands synchronous write passes to device global VRAM, schedules the linear kernel execution grid, and pulls the output back to host addresses.

Further down we will declare the arguments ‘a’ and ‘b’ in the call signature of our function as follows:

signature(a = "numeric", b = "numeric")

So in the first two lines of of the following C++ interface code we grab these two arguments and store them onto ‘NumericVector’ variables ‘r_a’ and ‘r_b’:

vector_interface_src <- '
NumericVector r_a(a);
NumericVector r_b(b);

Now we create a ‘NumericVector’ ‘r_c’ in appropriate size to carry the output vector:

int n = r_a.size();
NumericVector r_c(n);

In the following step we create ‘Memory’ objects to carry both the host and device memory. Note that you would have to write a whole bunch of low level CL calls to accomplish this:

Memory<real> gpu_a(*device, n);
Memory<real> gpu_b(*device, n);
Memory<real> gpu_c(*device, n);

We have to write our input vectors ‘r_a’ and ‘r_b’ into their ‘Memory’ counterparts ‘gpu_a’ and ‘gpu_b’:

for(int i = 0; i < n; ++i) {
    gpu_a[i] = r_a[i];
    gpu_b[i] = r_b[i];
}

The next beautiful feature of using the OpenCL Wrapper classes is the simplicity of transferring the host memory to the device memory.

gpu_a.write_to_device();
gpu_b.write_to_device();

Now we declare our kernel with its name and arguments. The ’*device’ pointer used here is prepared by ‘oclFunction’ and ‘inlineCL’ and references to a ready to use OpenCL ‘Device’ object.

Kernel k(*device, (ulong)n, "sigmoid_add_kernel", gpu_a, gpu_b, gpu_c, n);

Finally we can execute our kernel

k.run();

and transfer the device memory of the result variable ‘gpu_c’ back in read it in the Rcpp result vector ‘r_c’.

gpu_c.read_from_device();
for(int i = 0; i < n; ++i) {
    r_c[i] = gpu_c[i];
}
return r_c;

Now lets put this all together and save it as ‘./sigmoid_add_rcpp.cpp’

vector_interface_src <- '
NumericVector r_a(a);
NumericVector r_b(b);

int n = r_a.size();
NumericVector r_c(n);

Memory<real> gpu_a(*device, n);
Memory<real> gpu_b(*device, n);
Memory<real> gpu_c(*device, n);

for(int i = 0; i < n; ++i) {
    gpu_a[i] = r_a[i];
    gpu_b[i] = r_b[i];
}

gpu_a.write_to_device();
gpu_b.write_to_device();

Kernel k(*device, (ulong)n, "sigmoid_add_kernel", gpu_a, gpu_b, gpu_c, n);
k.run();

gpu_c.read_from_device();
for(int i = 0; i < n; ++i) {
    r_c[i] = gpu_c[i];
}

return r_c;
'
writeLines(vector_interface_src, "./sigmoid_add_rcpp.cpp")

The same logic with file search applies here: ‘./sigmoid_add_rcpp.cpp’ will be searched for locally, ‘sigmoid_add_rcpp.cpp’ will be read from a subdirectory ‘interface’ at the installed library path, in this case ‘system.file(“interface”, package = “OpenCLeaR”)’.

Section 1.4: Building the JIT compiled OpenCL R function

Now we stitch the two parts above together via ‘oclFunction’. Its call needs the aforementioned call signature and the file paths to a kernel,an interface and an optional mathematical library. I f the latter is omitted the ‘system’ library ‘libkernel.cl’ sitting at ‘system.file(“kernel”, package = “OpenCLeaR”)’ will be used. Remember that only functions which are really called at least once will be included in the OpenCL binary as they all are declared ‘static inline’-

Furthermore note that we embed the ‘OpenCLeaR::oclFunction’ into a IIEF (Immediately Invoked Function Expression, the ‘(function(){…})()’ construct) R wrapper using lexical scoping which makes it possible for this function to go into your own R library as other R functions, you can prepend a roxygen header containing your documentation, roxygen will recognize it as function to be exported into your NAMESPACE on so on.

You can look at the ‘runifOCL()’ functions in the source to learn how you can use this wrapping mechanism to cache the result of the ‘inlineCL’ compilation step.

sigmoid_vector_gpu <- (function() {
    .vector_gpu_internal <- NULL
    function(vec_x, vec_y) {
        if (is.null(.vector_gpu_internal)) {
            .vector_gpu_internal <<- OpenCLeaR::oclFunction(
                signature      = signature(a = "numeric", b = "numeric"),
                kernel_file    = "./sigmoid_add_kernel.cl",
                interface_file = "./sigmoid_add_rcpp.cpp",
                math_lib       = "./libkernel.cl"
                )
        }
        return(.vector_gpu_internal(a = vec_x, b = vec_y))
    }
})()

Section 1.6: Key OpenCL Design Principles Applied So Far

Before scaling up to multi-dimensional matrix operations in Part 2, let us review the core GPGPU constraints we already applied in our element-wise example—and one crucial rule we will need next:

  • The real Abstraction Layer (Applied in libkernel.cl & sigmoid_add_kernel.cl): We avoided raw float or double declarations in our kernels and Rcpp interfaces. Instead, OpenCLeaR defines real dynamically at compile time based on the active device’s FP64 capability, allowing the exact same code to run on both double-capable GPUs and single-precision hardware.
  • Explicit Constant Literals (Applied in compute_sigmoid): We explicitly cast and suffixed scalar constants as (real)1.0f. Uncasted literals like 1.0 default to 64-bit double in OpenCL C, which either triggers slow software emulation or causes compilation failures on pure single-precision (FP32) devices.
  • Memory Coalescing (Applied in Y[id] / c[id]): Adjacent threads (id = get_global_id(0)) read and write contiguous memory addresses (a[id], b[id], c[id]). This allows the GPU memory controller to bundle parallel memory transactions into unified cache bursts.
  • Minimal Branch Divergence (Applied in if (id < n)): Inside GPU warps/wavefronts, threads execute in lock-step. Aside from the single boundary guard if (id < n) at the end of the grid, our kernel avoids nested if-else branches so no worker threads sit idle.
  • Explicit Memory Space Boundaries (Applied in Kernel Signatures): OpenCL strictly separates memory pools (__global for main device VRAM, __local for fast work-group scratchpad memory, and __private for thread-local registers). In Part 1, all array pointers were explicitly qualified as __global.
  • Preparing for Part 2 – Column-Major Matrix Layout: R stores matrices column by column. When mapping 2D matrices onto a flat 1D thread grid (id = get_global_id(0)) in the upcoming dense layer kernels, consecutive threads must step down rows first (row = id % num_samples, col = id / num_samples) with matching index offsets (k * num_samples + row) to preserve memory coalescing.

Part 2: Scaling Up (Neural Network Single-Step Backpropagation)

To unlock the streaming multiprocessors, we increase architectural intensity to O(N³) by implementing a dense neural layer forward pass followed immediately by analytical backpropagation to isolate input error (Δ X), weight gradients (Δ W), and bias updates (Δ b).

Section 2.1: Generating the Forward Passage Kernel

The forward pass kernel maps the input transformations across the global execution thread grid. It calculates the linear activation of the dense layer by computing the inner product of the input matrices, injects the corresponding bias vector components, and maps the output matrix elements directly through the logistic activation function.

Note that we now execute the complete sum on a single compute node, the previous example we distributed the sum across all compute nodes. But in contrast to the previous example we compute now all weighted sums for a complete neural network in parallel. Each compute node represents a single neuron of our neural net.

nn_kernels_src <- '
__kernel void dense_forward_kernel(__global const real* X,
                                 __global const real* W,
                                 __global const real* b,
                                 __global real* Y,
                                 const int num_samples,
                                 const int in_features,
                                 const int out_features) {
    int id = get_global_id(0);
    int total_elements = num_samples * out_features;

    if (id < total_elements) {
        int row = id % num_samples;
        int col = id / num_samples;

        real sum = (real)0.0f;
        for (int k = 0; k < in_features; ++k) {
            sum += X[k * num_samples + row] * W[col * in_features + k];
        }
        sum += b[col];
        Y[id] = compute_sigmoid(sum);
    }
}
'
writeLines(nn_kernels_src, "./nn_forward_kernel.cl")

We write this standalone forward kernel to ./nn_forward_kernel.cl and create a matching Rcpp interface (./nn_forward_rcpp.cpp) to verify the pure forward pass against base R before adding the back-propagation steps:

forward_interface_src <- '

NumericVector r_b(b);

int num_samples  = r_X.nrow();

NumericMatrix r_Y(num_samples, out_features);

int size_W = in_features * out_features;

Memory<real> gpu_W(*device, size_W);

Memory<real> gpu_Y(*device, size_Y);

for(int i = 0; i < size_X; ++i) gpu_X[i] = r_X[i];
for(int i = 0; i < size_W; ++i) gpu_W[i] = r_W[i];
for(int i = 0; i < out_features; ++i) gpu_b[i] = r_b[i];

gpu_W.write_to_device();
gpu_b.write_to_device();

             gpu_X, gpu_W, gpu_b, gpu_Y, num_samples, in_features, out_features);

'

Section 2.2: Generating the Analytical Backward Pass Kernels

The backward pass requires a modular pipeline to isolate gradients: * Delta Kernel: Implements the chain rule by scaling the incoming loss gradient vector components with the analytical derivative (d_sigmoid) of the forward activation states. * Weights Kernel: Multiplies the transposed input space with the isolated delta tensor to assemble the weight gradient tracking metrics. * Inputs Kernel: Back-propagates the loss signal to preceding layers by projecting the delta states through the transposed weight coordinates. * Bias Kernel: Executes a fully parallelized row-reduction per output feature column, eliminating sequential reduction overhead on the device.

We now extend our mathematical library by a function ‘d_sigmoid’ which returns the derivative of the sigmoid function from above needed for optimizing weights via the back propagation rule:

libkernel_src <- '
static inline real compute_sigmoid(real x) {
    return (real)1.0f / ((real)1.0f + exp(-x));
}

static inline real d_sigmoid(real sigmoid_y) {
    return sigmoid_y * ((real)1.0f - sigmoid_y);
}
'
writeLines(libkernel_src, "./libkernel.cl")

Now we define the additional kernels (Note that you can collect more than a single kernel in a single file):

nn_kernels_src_extended <- '
__kernel void dense_backward_delta_kernel(__global const real* dY,
                                         __global const real* Y,
                                         __global real* dL,
                                         const int total_elements) {
    int id = get_global_id(0);
    if (id < total_elements) {
        dL[id] = dY[id] * d_sigmoid(Y[id]);
    }
}

__kernel void dense_backward_weights_kernel(__global const real* X,
                                          __global const real* dL,
                                          __global real* dW,
                                          const int num_samples,
                                          const int in_features,
                                          const int out_features) {
    int id = get_global_id(0);
    int total_elements = in_features * out_features;

    if (id < total_elements) {
        int row_w = id % in_features;
        int col_w = id / in_features;

        real sum = (real)0.0f;
        for (int i = 0; i < num_samples; ++i) {
            sum += X[row_w * num_samples + i] * dL[col_w * num_samples + i];
        }
        dW[id] = sum;
    }
}

__kernel void dense_backward_inputs_kernel(__global const real* dL,
                                         __global const real* W,
                                         __global real* dX,
                                         const int num_samples,
                                         const int in_features,
                                         const int out_features) {
    int id = get_global_id(0);
    int total_elements = num_samples * in_features;

    if (id < total_elements) {
        int row_x = id % num_samples;
        int col_x = id / num_samples;

        real sum = (real)0.0f;
        for (int j = 0; j < out_features; ++j) {
            sum += dL[j * num_samples + row_x] * W[j * in_features + col_x];
        }
        dX[id] = sum;
    }
}

__kernel void dense_backward_bias_kernel(__global const real* dL,
                                        __global real* db,
                                        const int num_samples,
                                        const int out_features) {
    int id = get_global_id(0);
    if (id < out_features) {
        real b_sum = (real)0.0f;
        int col_offset = id * num_samples;
        for (int i = 0; i < num_samples; ++i) {
            b_sum += dL[col_offset + i];
        }
        db[id] = b_sum;
    }
}
'
full_nn_kernels <- paste(nn_kernels_src, nn_kernels_src_extended, sep="\n")
writeLines(full_nn_kernels, "./nn_training_kernels.cl")

Section 2.3: Writing the Single-Step Rcpp Gateway Interface

The Rcpp gateway configures the unified host-device transactional layout for debugging single updates. It extracts matrix array meta-dimensions from R objects, reserves physical device memory nodes via ‘Memory’, pushes input tracking matrices to the device VRAM, and chains the sequential kernel submission queues. Note that this C++ interface calls not only a single kernel.

nn_interface_src <- '
NumericMatrix r_X(X);
NumericMatrix r_W(W);
NumericVector r_b(b);
NumericMatrix r_dY(dY);

int num_samples = r_X.nrow();
int in_features = r_X.ncol();
int out_features = r_W.ncol();

NumericMatrix r_Y(num_samples, out_features);
NumericMatrix r_dW(in_features, out_features);
NumericMatrix r_dX(num_samples, in_features);
NumericVector r_db(out_features);

int size_X = num_samples * in_features;
int size_W = in_features * out_features;
int size_Y = num_samples * out_features;

Memory<real> gpu_X(*device, size_X);
Memory<real> gpu_W(*device, size_W);
Memory<real> gpu_b(*device, out_features);
Memory<real> gpu_Y(*device, size_Y);
Memory<real> gpu_dY(*device, size_Y);
Memory<real> gpu_dL(*device, size_Y);
Memory<real> gpu_dW(*device, size_W);
Memory<real> gpu_dX(*device, size_X);
Memory<real> gpu_db(*device, out_features);

for(int i = 0; i < size_X; ++i) gpu_X[i] = r_X[i];
for(int i = 0; i < size_W; ++i) gpu_W[i] = r_W[i];
for(int i = 0; i < out_features; ++i) gpu_b[i] = r_b[i];
for(int i = 0; i < size_Y; ++i) gpu_dY[i] = r_dY[i];

gpu_X.write_to_device();
gpu_W.write_to_device();
gpu_b.write_to_device();
gpu_dY.write_to_device();

Kernel k_fwd(*device, (ulong)size_Y, "dense_forward_kernel", gpu_X, gpu_W, gpu_b, gpu_Y, num_samples, in_features, out_features);
k_fwd.run();

Kernel k_delta(*device, (ulong)size_Y, "dense_backward_delta_kernel", gpu_dY, gpu_Y, gpu_dL, size_Y);
k_delta.run();

Part 3: Fully Enclosed Multi-Epoch VRAM Training Loop Optimization

To reach maximum execution efficiency, we eliminate iterative bus communication entirely. By introducing an optimizer_kernel and wrapping an explicit training loop inside Rcpp, data remains strictly persistent within global GPU VRAM across multiple epochs. Note that in this example we combine the call to different kernels loaded from a single file into one interface.

Section 3.1: Appending the In-Place VRAM SGD Optimizer

The structural optimizer kernel updates parameter maps directly within device global memory addresses. By decoupling mathematical step transformations from host dependencies, it applies parameter weights corrections natively in local space coordinates.

optimizer_kernel_src <- '
__kernel void optimizer_kernel(__global real* W,
                               __global real* b,
                               __global const real* dW,
                               __global const real* db,
                               const real learning_rate,
                               const int size_W,
                               const int out_features) {
    int id = get_global_id(0);
    if (id < size_W) {
        W[id] -= learning_rate * dW[id];
    }
    if (id < out_features) {
        b[id] -= learning_rate * db[id];
    }
}
'
full_kernels_src <- paste(readLines("./nn_training_kernels.cl"), collapse="\n")
full_kernels_src <- paste(full_kernels_src, optimizer_kernel_src, sep="\n")

The closed tracking loop operates entirely inside the C++ runtime module. Host matrices are written once to the device, persistent execution references cycle through backpropagation chains for the given epoch ceiling, and parameters update on-chip before final matrices pass back to host scopes.

Part 4: Statistical Application – Non-Linear Binary Classification

To demonstrate that our enclosed GPGPU neural network solves real statistical estimation problems, we apply it to a non-linear binary classification task. Section 4.1: Adding an On-Device MSE Loss Gradient Kernel

In Part 3, the error gradient dY was fixed externally. For real multi-epoch training, the residual gradient \(\frac{\partial L}{\partial \hat{y}} = \frac{2}{N}(\hat{y} - y)\) must be updated directly inside GPU VRAM after each forward pass.

loss_kernel_src <- '
__kernel void mse_grad_kernel(__global const real* Y_pred,
                              __global const real* Y_true,
                              __global real* dY,
                              const int total_elements) {
    int id = get_global_id(0);
    if (id < total_elements) {
        dY[id] = ((real)2.0f / (real)total_elements) * (Y_pred[id] - Y_true[id]);
    }
}
'

Part 5: Guidelines for Package Developers – Packaging Multi-Kernel JIT Pipelines

If you want to include custom GPGPU functionalities into your own redistributable R package, you can leverage OpenCLeaR::oclFunction inside an Immediately Invoked Function Expression (IIFE) using lexical scoping. This structural pattern provides an elegant on-the-fly caching mechanism: the expensive multi-kernel compilation step happens exactly once during the very first invocation, while subsequent training cycles instantly execute the pre-compiled VRAM pipeline.

To make a complex architecture like our multi-epoch neural classifier fully compliant with CRAN policies and roxygen2 documentation pipelines, you can package it using the following blueprint:

# 1. Register the hidden closure variable as a global to prevent CRAN check notes
if (getRversion() >= "2.15.1") {
  utils::globalVariables(".nn_classify_gpu_internal")
}

##' Enclosed Multi-Epoch Neural Network Training via OpenCL
##' 
##' This function demonstrates how to wrap a complex OpenCLeaR JIT-compiled 
##' multi-kernel pipeline into a standard R package function utilizing 
##' a persistent closure cache.
##' 
##' @name nn_classify_gpu
##' @param X_mat     A numeric design matrix containing input features.
##' @param W_mat     A numeric matrix representing initial layer weights.
##' @param b_vec     A numeric vector containing layer biases.
##' @param Y_mat     A numeric matrix containing observed target variables.
##' @param lr     The learning rate parameter for the SGD optimizer.
##' @param num_epochs The total number of training epochs to run entirely in VRAM.
##' @param ...        Arguments passed through to \code{\link{oclFunction}} like \code{verbose} or \code{force_float}.
##' @return A list containing the updated weight matrix \code{W}, the bias vector \code{b}, and predicted probabilities \code{Y_pred}.
##' @export
nn_classify_gpu <- (function() {
  # This variable remains persistent in the function's enclosing environment
  .nn_classify_gpu_internal <- NULL
  
  function(X_mat, W_mat, b_vec, Y_mat, lr, num_epochs, ...) {
    if (is.null(.nn_classify_gpu_internal)) {
      # The JIT compilation triggers ONLY on the first call
      .nn_classify_gpu_internal <<- OpenCLeaR::oclFunction(
        signature = signature(X       = "matrix", 
                              W       = "matrix", 
                              b       = "numeric", 
                              Y_true  = "matrix", 
                              lr      = "numeric", 
                              epochs_in = "integer"),
        kernel_file    = "nn_stat_kernels.cl",
        interface_file = "nn_stat_rcpp.cpp",
        math_lib       = "libkernel.cl",
        ...
      )
    }
    # Direct execution of the cached binary pointer
    return(.nn_classify_gpu_internal(X = X_mat, W = W_mat, b = b_vec, Y_true = Y_mat, lr = lr, epochs_in = num_epochs))
  }
})()

Architectural Key Takeaways for Developers:

  • The Global Variables Shield: CRAN checks strictly flag assignments to external environments (<<-). Pre-registering your internal pointer name (e.g., .nn_classify_gpu_internal) via utils::globalVariables() ensures a completely clean R CMD check without any architectural NOTEs.
  • Roxygen2 Integration: Because the IIFE evaluates immediately during package loading, roxygen2::roxygenise() can parse the preceding comment block normally. It extracts the @param documentation, generates the standard .Rd help files, and safely places the export(nn_classify_gpu) directive into your package’s NAMESPACE.
  • Path Resolution: When shipping kernels inside a package, omit the leading ./ in kernel_file and interface_file. OpenCLeaR will then automatically search for them within the kernel/ and interface/ subdirectories of your installed library structure.
  • Forwarding Controls via Dot-Dot-Dot: Passing ... straight into oclFunction allows your package users to seamlessly inject hardware control flags at runtime (such as forcing single-precision compilation using force_float = TRUE) without changing a single line of your C++ backend code. ```

Conclusion

Across this vignette, we progressed from a simple element-wise vector operation to a complete, self-contained statistical learning pipeline running entirely in GPU VRAM:

  1. Portability without Code Changes: Using OpenCLeaR’s real type abstraction and automatic JIT caching, identical OpenCL C kernels executed seamlessly across both FP64-capable discrete GPUs and FP32-only integrated graphics.
  2. Eliminating PCIe Bottlenecks: While single element-wise vector operations (Part 1) are bounded by host-to-device memory transfers, keeping iterative matrix operations and parameter updates persistent inside device VRAM across epochs (Parts 3 & 4) unlocks substantial speedups.
  3. Statistical Integrity: Both the multi-epoch gradient benchmarks and the non-linear binary classification example confirmed that GPU-accelerated training recovers true underlying parameters and decision boundaries with high numerical precision.
